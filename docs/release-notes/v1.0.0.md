# Bogie v1.0.0 — release notes (draft)

> **Draft.** This file is prepared ahead of the tag. v1.0.0 is not tagged and
> no GitHub release exists yet. It becomes the release text only once the
> maintainer tags `v1.0.0`, which comes after #41, #42 and this PR are merged.

v1.0.0 is the first stable release. It adds almost nothing on top of v0.7.0:
two small fixes, plus a promise. The APIs listed under **The 1.0
compatibility promise** below stay as they are for every 1.x release.

## What changed since v0.7.0

`git log v0.7.0..origin/main` is empty at the time of writing: `main` is
still the v0.7.0 commit (`d16ffec`). Everything in v1.0.0 is in these PRs:

- **`bogie db:status -h` / `--help` / `help` print usage** (#41). Before
  this, `db:status --help` said `db:status: takes no arguments`, because the
  command rejected every argument before it could print usage. It now uses
  the same `WantsHelp` hook `doctor` got in v0.7.0 (#37). Help prints and
  exits 0 both outside an app and inside one, before Bogie looks for
  `bogie.toml` or connects to the database. Any other argument is still
  refused, and the error now points at `bogie db:status -h`.
- **Generated `AGENTS.md`: `model:sync` takes a table** (#42). The **Files
  the generators own** section told assistants to run
  `bogie model:sync <model>`. The command takes a table name,
  `bogie model:sync [TABLE]` (for example `bogie model:sync users`), and the
  later paragraph in the same file already said so. Both places now agree.
  Existing apps get the fix from `bogie app:update`.
- **Docs**: `docs/STATUS.md` is brought up to date, and this file is added
  (this PR).

For what v0.7.0 itself added (`bogie g policy`, `g scaffold --policy`,
`bogie db:status`, `g job --every`, the token `role` claim and `MintFor`,
`doctor -h`, `make up` printing the published port, and the AGENTS.md
section), see the
[v0.7.0 release](https://github.com/bogie-go/bogie/releases/tag/v0.7.0).

## The 1.0 compatibility promise

From v1.0.0, every 1.x release keeps the following generated APIs and tool
behaviour as they are. A change that breaks any of them waits for 2.0. New
optional things can still be added: a new field, a new function, a new flag.

- **`token.Maker.MintFor(subject, role string, ttl time.Duration) (string, error)`**
  in `app/services/token`. `Mint(subject, ttl)` stays a wrapper that calls
  `MintFor` with an empty role. `Claims` keeps `Subject`, `Role`,
  `ExpiresAt` and `ID`. The role travels as the optional JWT claim
  `"role"` (`omitempty`).
- **`middlewares.Role(c *gin.Context) string`** in `app/middlewares`, next
  to `middlewares.Subject(c)`. It returns the role string the token
  carried, or `""` when the token had none or the route is not behind
  `RequireUser`.
- **`jobs.Workers(log *slog.Logger) (*river.Workers, []*river.PeriodicJob, bool)`**
  in `app/jobs`, three values: the workers, the periodic jobs, and whether
  any worker is registered. `app/application.go` reads all three. It hands
  the periodic slice to `river.Config.PeriodicJobs` and runs insert-only
  while the bool is false.
- **`policies.Actor`**, the struct `{ ID string; Role string }` in
  `app/policies`. A policy method takes an `Actor` and a `*models.<Model>`
  and returns `bool`.
- **`policies.ErrDenied`**, the error a policied service returns on a
  refusal. A controller checks it with `errors.Is` and answers 403, in the
  same switch as `models.ErrNotFound` (404) and `models.ErrInvalid` (422).
- **`bogie g job NAME --every CRON`**. The schedule is robfig/cron
  `ParseStandard`: five fields, `@daily`-style descriptors, or a
  `CRON_TZ=` prefix. The job is registered as a River `PeriodicJob` with
  `RunOnStart: false`. `bogie d job` removes the schedule with the worker,
  and `--pretend` writes nothing. **A restart can skip a run, and this is
  documented behaviour, not a bug.** River's elected leader is the only
  client that inserts periodic jobs, and it keeps the schedule in memory. A
  run that falls due while the leader restarts, or while a new leader is
  elected, is not made up afterwards. `RunOnStart` is off, so a new leader
  does not enqueue one on election either. See `docs/DESIGN.md` §9, item 6b
  ("Periodic jobs"). A job that must not miss a run should record its last
  run in the database and catch up itself.

The role is optional, and it is not a session:

> The token's role claim is optional (MintFor sets it; Mint makes tokens without a role); apps that need revocation should check the database.

A role is only a string that a policy reads. Bogie has no role table, and
it never loads a user. A token stays valid until it expires, even after the
user's role changes. If an app has to withdraw access sooner, it should look
the user up (or keep a deny-list keyed on `Claims.ID`) in the database,
rather than trust the claim alone.

## Upgrading

```sh
go install github.com/bogie-go/bogie@v1.0.0
bogie app:update --pretend   # see the plan
bogie app:update
```

On an app that is already on v0.7.0, `app:update` brings in the one-line
AGENTS.md fix and sets `bogie.toml` to `v1.0.0`. An app on v0.6.8 or older
should first follow the v0.7.0 notes (the periodic-job slice in
`app/jobs/jobs.go` and `app/application.go`), which `app:update` merges in
the same run.

### Token apps: `app:update` does not move them onto MintFor, Claims.Role or middlewares.Role

If an app ran `bogie g authentication token` **before v0.7.0**, its token
files predate the role claim. `app:update` does **not** rewrite them. The
app keeps building and `Mint` keeps working, but `MintFor`, `Claims.Role`
and `middlewares.Role` do not exist in it. Code written against the 1.0
API, and `bogie g scaffold ... --policy` (whose controller calls
`middlewares.Role(c)`), will not compile until you add them. `bogie g policy`
on its own does compile, because it only needs `policies.Actor`, but every
actor's `Role` stays `""`.

Check first. If this prints nothing, the app needs the manual steps:

```sh
grep -n 'func (m Maker) MintFor' app/services/token/token.go
grep -n 'func Role' app/middlewares/require_user.go
```

**Manual steps.** These are the same edits the v0.7.0 generator makes. Do
them on a clean, committed tree:

1. **`app/services/token/token.go`**
   - Add `Role string` to `Claims`, between `Subject` and `ExpiresAt`.
   - Add the JWT payload type:
     ```go
     // signedClaims is the JWT payload: the registered claims plus an optional role.
     type signedClaims struct {
         Role string `json:"role,omitempty"`
         jwt.RegisteredClaims
     }
     ```
   - Rename the body of `Mint` to a new method
     `func (m Maker) MintFor(subject, role string, ttl time.Duration) (string, error)`.
     Its claims become `signedClaims{Role: role, RegisteredClaims: jwt.RegisteredClaims{...}}`,
     with the same Issuer, Subject, IssuedAt, ExpiresAt and ID as before.
   - Make `Mint` a wrapper: `return m.MintFor(subject, "", ttl)`.
   - In `Verify`, parse into `var claims signedClaims` instead of
     `jwt.RegisteredClaims`, and return `Role: claims.Role` in the `Claims`.
2. **`app/middlewares/require_user.go`**
   - Next to `subjectKey`, add `roleKey = "role"`.
   - In `RequireUser`, after `c.Set(subjectKey, claims.Subject)`, add
     `c.Set(roleKey, claims.Role)`.
   - Add:
     ```go
     // Role is the role string the request's token carried, or "" when it carried
     // none or RequireUser does not guard the route.
     func Role(c *gin.Context) string { return c.GetString(roleKey) }
     ```
3. **Specs (optional, recommended).** In `app/services/token/token_test.go`,
   add a `MintFor` case: mint with `"admin"`, verify, and expect
   `claims.Role` to be `"admin"`. Also check that a plain `Mint` token has
   an empty `Role`.
4. **Wherever the app signs users in**, call `MintFor(userID, role, ttl)`
   where a role is known. Existing `Mint` calls can stay: they make tokens
   without a role.
5. Run `bin/ci`.

Tokens issued before this change have no `role` claim. They still verify,
and `Claims.Role` / `middlewares.Role(c)` is `""` for them until they
expire.

Instead of step 1 and step 2, you can run `bogie g authentication token`
again in a scratch app at the same version and copy the two files over, or
run it in the app itself after porting your hand edits (files you changed
are reported `conflict` until you pass `--force`). Either way, diff the
result before you commit.

Policies have no upgrade step. `bogie g policy` and `--policy` are new in
v0.7.0, so no older app has a policy for `app:update` to move. Their files
(`app/policies/actor.go`, `<name>_policy.go` and the service) are written
once by the generator and left alone afterwards.
